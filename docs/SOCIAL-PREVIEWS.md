# Social previews

## Art direction and asset pipeline
Thirteen 1200×630 RGB JPEG covers are generated by `scripts/social-images.mjs` before export. A wide project photograph fills the top 440px. A cool-paper lower band carries deterministic Archivo typography, a small signal-blue rule and the section/slash mark. Text is kept within the central 630px crop where possible. The home cover reads “SECTION / OFFICE” and “Architecture & Interiors.” Each project uses its own hero image and project title. Articles use relevant project photography and their own title.

The script reads actual licensed Archivo WOFF glyphs and composes their outlines. Text is not part of the generated architectural image and the cover is not a screenshot of the webpage. Each source contour is serialized without mutating cached glyphs, then positioned and scaled as a separate SVG path. This avoids contextual-substitution and contour-optimization defects in small type.

`public/social/manifest.json` is the generated file manifest with dimensions, source image, title and actual bytes. All covers are below the 500 KB target; the largest is approximately 143 KB. Final exact values are generated in the table below.

## Route mapping
- `/` → `home-v1.jpg`.
- `/work/{slug}/` → `{project-slug}-v1.jpg`, all eight known projects.
- `/journal/{slug}/` → `{article-slug}-v1.jpg`, all three articles.
- Remaining public routes → `fallback-v1.jpg`.

`lib/metadata.ts` defines accurate titles/descriptions, one canonical URL, OG title/description/type/URL/site_name/image/width/height/alt, and Twitter summary_large_image/title/description/image. Every route’s values are emitted in exported HTML. No browser state or runtime social endpoint is involved. Root file-based image metadata is deliberately absent so it cannot override item-specific covers.

## Public origin
`SITE_URL` is the single validated build-time origin. Local builds default to `http://localhost:3000`. Public builds must use an actual HTTPS origin with no path, query, hash or credentials. The validation rejects insecure public origins and example.com. `.env.example` contains only this non-secret setting.

```sh
SITE_URL='https://YOUR-ACTUAL-DEPLOYMENT-HOST' npm run build
SITE_URL='https://YOUR-ACTUAL-DEPLOYMENT-HOST' npm run verify:export
```

The quoted host is a substitution instruction, not a claimed domain. Deploy `out/` only after authorization. A build using localhost cannot be fetched by outside chat services. A port or host change is a new browser origin and has separate local records.

## Actual local verification
`npm run verify:export` checks all 23 public routes and writes `docs/export-verification.json`. It reads files without application JavaScript and checks single/non-conflicting required tags, exact canonicals and origins, correct project/article cover mapping, JPEG format, 1200×630 dimensions, file presence and the size target. It also checks all 30 project images and the useful 404.

Full covers, 360×189 thumbnails and centered 360×360 crops are inspected locally. These are visual tests, not platform unfurls. Inspection assets are in `docs/screenshots/covers/`.

## Deployment-dependent checks
After an authorized public deployment:

1. Fetch the homepage and representative nested project/article routes without cookies. Verify 200 and `text/html`; inspect canonical/OG/Twitter values directly in the response HTML.
2. Fetch every referenced image URL. Verify HTTPS, 200, `image/jpeg`, correct dimensions and no expiring signature or login/protection page.
3. Check all project-specific images against the fixture mapping; a successful fallback image is still an error on a project URL.
4. Use appropriate public preview tools such as Facebook Sharing Debugger or LinkedIn Post Inspector if available. Test direct links without sending unsolicited messages or posting to other people.
5. Record the host, date, returned metadata and actual unfurl evidence separately from local screenshots.

Pages discourage indexing with `noindex, follow`. `robots.txt` allows fetching; it does not blanket-disallow crawlers. This is not a guarantee of identical behavior across platforms.

## Caching
Image filenames are explicitly versioned (`-v1.jpg`). If a composition changes after deployment, generate a new versioned name, update metadata and redeploy the matching HTML. Platform debugging/refresh tools may request a recrawl; they do not promise an immediate cache purge. Platforms can cache titles/images, crop differently, suppress cards or respect user-specific settings.

No public deployment or live platform-preview verification has been performed. Those are the only external preview checks pending.
